### 缓存、档案与保存任务的边界

`5946c0` 每组缓存步长为 `0x28`，包含武器、六个配件槽及存在标志，脏标志位于该组偏移 `0x24`。`5948f0` 遍历 12 × 5 × 2 个槽位组合，对脏缓存做校验，再调用 `592b10`，随后清除脏标志并在档案状态为 0 或 2 时设置档案待保存标志。

`592b10` 使用 `weaponClasses`、组合索引除以 2、主副武器前缀构造字段路径：`primaryBase` / `secondaryBase` 和 `primaryAttach` / `secondaryAttach`，后者再附加六槽索引。`5926d0` 检查 DDL 资源大小与路径后交给类型写入器。字段名来自 [EXE 字符串字节记录](evidence/round2/profile-field-strings.json)。

同一字节记录还确认 `695a10` 使用 `onboardCharacterID`，`7051e0` 使用 `currentCharacterIndex`。客户端档案缓存改变、后续保存任务发出、服务端落盘及重登恢复是不同观察层次；本次只取证静态代码。

## 取证与保留项

- 函数标签是分析命名，原始伪代码不改写。旧主文件保持稳定，新结果进入变体和来源列表。
- `call-chains.json` 保存直接调用与未解析的间接调用；虚表调用、函数指针、尾跳转及控制流可达性不被自动补成确定的调用边。
- REA 成功加载匹配快照。复用反编译查询未在客户端 300 秒窗口内完成，记录在 [REA 查询结果](evidence/round2/rea-cached-query.json)。本轮没有确认该查询缓存命中，不把独立 Ghidra 结果标为 REA 新 Evidence。
- REA 会话已关闭并保存 [结束快照](evidence/round2/rea-end.rea.json)，可复用的历史工作流绑定仍为 71 个；快照不代表一次新的完整 Ghidra 分析。
- 所有结论限于静态证据。没有运行游戏、修改存档或验证在线账号、购买和装备行为。
